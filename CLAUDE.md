# CLAUDE.md — League Companion

Личный трекер статистики League of Legends. Go-бэкенд (Riot API) + Android-клиент (Kotlin/Compose).

## Перед началом любой работы

1. Прочитай полностью `SPEC.md` — это техническое задание, источник истины по функциональности.
2. Прочитай `PROGRESS.md` — текущее состояние проекта, что уже сделано, что в работе.
3. Секция «Отклонения от SPEC.md» ниже имеет приоритет над `SPEC.md`, если они расходятся.

## Стек (зафиксировано, не менять по ходу проекта)

- Backend: Go 1.22+, роутер — **chi** (решено; не переключайся на gin на середине проекта)
- БД: PostgreSQL 16, миграции — golang-migrate
- Кэш: Redis (см. SPEC.md 3.1)
- Android: Kotlin, Jetpack Compose, MVVM, StateFlow, Room, Retrofit + OkHttp, Hilt

## Отклонения от SPEC.md (приняты, реализовывать именно так)

1. **Хранение матчей.** Помимо распарсенных полей в `match_participants`, добавить колонку `raw_data JSONB` в `matches` — писать туда полный JSON-ответ Match-V5 при первой синхронизации. Цель: расширение набора полей (предметы, руны, спеллы) в будущем не должно требовать повторных запросов к Riot — данные уже лежат локально.
2. **Идемпотентность.** Все `INSERT` в `matches` и `match_participants` — через `ON CONFLICT DO NOTHING`. Несколько отслеживаемых саммонеров могут встретиться в одном матче и синхронизироваться параллельно — гонка на `match_id` реальна.
3. **Auth Android↔Backend.** Shared-secret заголовок `X-API-Key`, проверяется middleware на всех `/api/v1/*`, кроме health-check. Значение — в `.env` бэкенда и в конфиге Android-клиента (BuildConfig, не хардкодить).
4. **Sync worker.** Добавить guard от наложения синхронизаций — atomic bool `syncInProgress`; если предыдущий прогон тикера ещё не завершился, следующий тик пропускается с логом, а не встаёт в очередь.

## Конвенции

- Перед каждым коммитом: `gofmt -l .`, `go vet ./...`, `golangci-lint run` (backend); ktlint/Android lint (android). Ничего не коммитить, если эти проверки красные.
- TDD для трёх компонентов, явно требуемых в DoD: rate limiter, region routing mapping, агрегация статистики — сначала тест, потом реализация.
- Один коммит = одна логическая фича. Conventional Commits со scope: `type(scope): описание`, где `scope` — `backend` или `android`. Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`. Примеры: `feat(backend): add composite rate limiter`, `fix(android): handle empty match history state`.
- Секреты (`RIOT_API_KEY`, `X-API-Key`) — только через `.env` / переменные окружения. Никогда не коммитить, не печатать в логи, не подставлять в тестовые фикстуры как реальные значения.

## Как работать по вехам

Разработка идёт вехами из `SPEC.md`, раздел 5 («План разработки»), они же — секции в `PROGRESS.md`. На каждую веху:

1. **План.** Сформулируй план изменений по текущей вехе (какие файлы, какие структуры, какие тесты) — как обзор перед реализацией, дождись подтверждения, не пиши код сразу.
2. **Реализация** по подтверждённому плану.
3. **Проверка.** Прогони тесты, при необходимости запусти `code-reviewer` subagent.
4. **Обнови `PROGRESS.md`** — отметь завершённые пункты, при необходимости допиши в «Журнал решений», если по ходу веха принято архитектурное решение, не описанное здесь.
5. **Коммит.**

Не пытайся закрыть несколько вех за один присест без промежуточных коммитов и обновления `PROGRESS.md` — это единственный способ восстановить контекст в следующей сессии.

## Effort

- Архитектурные решения, конкурентность (rate limiter, sync worker, обработка гонок) — `xhigh`.
- Отладка нестабильных багов (гонки, edge-cases 429) — `xhigh`.
- Типовые REST-хендлеры и Compose-экраны по уже согласованному плану — `high` или ниже, не трать бюджет зря на то, что уже решено архитектурно.

## Riot API

- Ключ протухает раз в 24 часа, обновляется вручную на developer.riotgames.com — это ожидаемо, не пытайся «чинить» истёкший ключ кодом.
- Region routing (platform vs regional) — только через выделенную функцию маппинга с юнит-тестом, см. SPEC.md 3.2 и риски в SPEC.md 7.
